# Design — STWV Management Platform

This document describes the system architecture: how the monorepo is laid
out, how data flows between layers, and the key design decisions you'd
need to know to safely change anything.

For day-to-day operating notes (workflows, ports, deploy) see
[replit.md](./replit.md). For end-user/admin documentation see
[docs/admin-guide.md](./docs/admin-guide.md).

---

## 1. High-level shape

```
┌──────────────────────────────────────────────────────────────────┐
│                        Browser (Clerk auth)                       │
│  React + Vite + TanStack Query + wouter + shadcn/ui + Tailwind v4 │
└───────────────────────────┬──────────────────────────────────────┘
                            │  HTTP /api/* (Bearer JWT)
┌───────────────────────────▼──────────────────────────────────────┐
│              artifacts/api-server (Express 5, esbuild)            │
│  Clerk JWT verify → loadDbUser → role middleware → route handlers │
│  All response shapes pinned by lib/api-spec/openapi.yaml          │
└───────────────────────────┬──────────────────────────────────────┘
                            │  Drizzle ORM (node-postgres pool)
┌───────────────────────────▼──────────────────────────────────────┐
│                        PostgreSQL 16                              │
│   23 tables · `audit_logs` is append-only via DB triggers         │
└──────────────────────────────────────────────────────────────────┘
```

Auth is **Clerk-only** — there are no local passwords. Every API request
carries a Clerk JWT in `Authorization: Bearer …`. The API server resolves
the JWT to a row in `users` (matching by `clerk_user_id`) before any
business logic runs.

## 2. Monorepo layout

```
artifacts/
  api-server/          Express REST API, deployed as the autoscale service
  mgmt/                React+Vite frontend, served at the root path "/"
  mockup-sandbox/      Component preview canvas (design-only, not user-facing)

lib/
  db/                  Drizzle schema + migrations + seed
  api-spec/            OpenAPI 3.1 spec (single source of truth) + Orval
  api-client-react/    Generated React Query hooks (consumed by mgmt)
  api-zod/             Generated Zod schemas (consumed by api-server)

scripts/               Repo-wide tsx scripts (post-merge hook, etc.)
```

Workspaces are wired by `pnpm-workspace.yaml`. TypeScript project
references are configured via `tsconfig.base.json`.

### Why split api-spec / api-client-react / api-zod?

- The OpenAPI YAML is the contract. Both client and server are derived
  from it, which means request/response shapes can never silently drift.
- Codegen runs via `pnpm --filter @workspace/api-spec run codegen`. After
  any spec edit you must regenerate, then run `pnpm typecheck` to surface
  consumers that need updating.

## 3. Data model

The schema lives in `lib/db/src/schema/`, one file per table, re-exported
from `index.ts`. There are **23 tables**; the canonical list is in
[replit.md](./replit.md#database-schema). Highlights:

- **Tenancy** — every project, invoice, offer, and contract is tied to one
  of the 4 `companies` rows. `users` are linked to companies through the
  `user_company_assignments` junction (an admin can belong to all 4).
- **RBAC** — `users.role` is one of 6 enum values
  (`admin`, `germany_accountant`, `india_accountant`, `project_manager`,
  `client`, `freelancer`). The `user_roles` reference table holds display
  names + descriptions for the UI.
- **Money** — currency-sensitive columns (`amount`, `hourly_rate`, etc.)
  are stored as `numeric(12,2)` and serialized as decimal strings to avoid
  JS float precision bugs.
- **Audit log** — `audit_logs` is **append-only** at the database layer.
  Triggers `audit_logs_no_update` and `audit_logs_no_delete` raise on
  UPDATE/DELETE so the trail can't be tampered with even by a DB
  superuser running the application code.
- **Invoice numbering** — `invoice_sequences (company_id, year, next_seq)`
  guarantees per-entity, per-year, gap-free invoice numbers under
  concurrent inserts.

### Migrations

All schema changes are tracked as SQL files in `lib/db/drizzle/`,
generated by `drizzle-kit generate` from the TypeScript schema. Custom
migrations (triggers, seed data, etc.) are added by hand and registered
in `drizzle/meta/_journal.json`. **`drizzle-kit push` is no longer used.**

See [memory.md → Database & migrations](./memory.md#database--migrations).

## 4. API server (artifacts/api-server)

- **Entry**: `src/index.ts` (binds to `process.env.PORT`).
- **App composition**: `src/app.ts` wires CORS, body parsing,
  cookie-parser, `pino-http` logging, the Clerk frontend-API proxy
  (`middlewares/clerkProxyMiddleware.ts`), the Clerk JWT middleware, and
  the route registry.
- **Routes**: `src/routes/index.ts` mounts route modules under `/api/*`.
  Each module follows the pattern
  `requireAuth → loadDbUser → requireRole → handler` so authorization is
  consistent and obvious.
- **Validation**: every body/query parses through a generated Zod schema
  from `@workspace/api-zod`. Anything that doesn't go through Zod gets a
  hand-written schema in the same module.
- **Errors**: thrown errors are caught by `errorMiddleware.ts` which maps
  known codes (Zod, Drizzle UniqueViolation, Clerk auth) to clean
  HTTP responses.
- **Build**: `build.mjs` calls esbuild to produce `dist/index.mjs`. Pino's
  worker thread requires the `esbuild-plugin-pino` to bundle correctly.

### Key cross-cutting concerns

| Concern | File | Notes |
|---------|------|-------|
| Auth (verify JWT) | `@clerk/express` `clerkMiddleware` | mounted in `app.ts` |
| Load `req.dbUser` | `middlewares/requireRole.ts` → `loadDbUser` | 403 if Clerk user has no DB row |
| Role gates | `requireAdmin`, `requireReader`, etc. | composable per-route |
| Audit logging | `lib/audit.ts` | called from mutating handlers; never logs the JWT |
| Tax engine | `lib/tax/` | Germany VAT, India CGST/SGST/IGST auto-detection |
| Recurring invoice scheduler | `lib/recurringInvoices.ts` | runs every 6h via setInterval inside the api-server process |

## 5. Frontend (artifacts/mgmt)

- **Routing**: `wouter` with a small `PrivateRoute` wrapper that checks
  `useAuth().isSignedIn` and (optionally) the user's role from
  `useGetMe()`.
- **Auth bridge**: `ApiTokenBridge` calls `setAuthTokenGetter` on the
  generated client so every fetch carries a fresh Clerk JWT.
- **Data**: TanStack Query via the generated hooks in
  `@workspace/api-client-react`. No hand-written `fetch` calls except
  inside the auth bridge.
- **UI**: shadcn/ui (Radix + Tailwind v4), `lucide-react` icons,
  `framer-motion` for transitions. Page tree is in `src/pages/`,
  reusable bits in `src/components/`.
- **Sidebar**: `components/layout/Sidebar.tsx` filters nav items by the
  current user's role and shows their identity + sign-out at the bottom.

### Page → role matrix

| Path | Allowed roles |
|------|---------------|
| `/dashboard` | admin, accountants, project_manager |
| `/companies`, `/companies/:id` | admin, accountants, project_manager |
| `/users`, `/users/:id` | admin only |
| `/projects`, `/projects/:id` | role-filtered server-side; PM/admin/accountants see all |
| `/time-tracking` | all (own entries; admins/accountants see all) |
| `/todos` | role-filtered |
| `/client-portal` | client |
| `/freelancer-portal` | freelancer |
| `/documents`, `/offers`, `/contracts`, `/invoices` | admin + accountants + PM |
| `/communication-hub` | all signed-in roles (per-project membership enforced) |
| `/compliance` | admin + accountants |
| `/settings` | all |

## 6. Codegen flow

```
lib/api-spec/openapi.yaml
        │
        │ pnpm --filter @workspace/api-spec run codegen
        ▼
lib/api-client-react/src/generated/    (React Query hooks)
lib/api-zod/src/generated/             (Zod schemas)
        │
        ├─► consumed by artifacts/mgmt        (hooks)
        └─► consumed by artifacts/api-server  (validation)
```

After editing the spec, always run codegen and `pnpm run typecheck` —
typecheck failures are how you find consumers that need updating.

## 7. Key design decisions

- **OpenAPI as the contract.** Hand-written types on either side would
  drift; codegen guarantees they don't.
- **Clerk for auth.** No local password store, no JWT signing of our
  own. Clerk dev keys locally, live keys auto-swapped on deploy.
- **Drizzle migrations only.** `push` is dangerous in any shared
  environment; the repo enforces `generate` + `migrate`.
- **Append-only audit log at the DB layer.** Application code can be
  buggy; triggers are the last line of defence.
- **Numeric money as strings.** Avoids JS float precision; Zod parses
  them as decimal strings.
- **Single Postgres, multi-tenant by `company_id`.** Cheaper to operate
  than 4 separate DBs, and cross-entity reports (Document Centre, weekly
  summary) become trivial joins.
- **Path-based artifact routing on Replit.** The frontend serves at `/`
  and proxies `/api/*` to the api-server artifact.

## 8. Where to add things

| You want to add… | Touch these |
|------------------|-------------|
| A new table | `lib/db/src/schema/<name>.ts`, re-export from `index.ts`, then `pnpm db:generate -- --name <desc>` |
| A new endpoint | `lib/api-spec/openapi.yaml` → codegen → handler in `artifacts/api-server/src/routes/` |
| A new page | `artifacts/mgmt/src/pages/<name>.tsx`, register in `App.tsx`, gate via `PrivateRoute` |
| A new role-restricted action | extend `requireRole.ts` (server) and the `PrivateRoute` allow-list (client) |
| A new background job | extend `lib/recurringInvoices.ts` pattern: setInterval inside api-server, idempotent handler |
